# ТЗ: личный кабинет пациента сети МедКвадрат

Версия 1.5 — 15.10.2026 (решения D1–D7, Q11, Q12, Q18; сверка ChatGPT; результаты проверок S0–S18).
Связанные документы: `00_KNOWLEDGE_BASE_MEDIALOG.md` (факты о базе), `02_WORKFLOW.md`
(кто что делает), `03_VERIFICATION_SQL.sql` (проверки только на чтение),
`04_RUNBOOK_BOOKING_CAPTURE.md` (снятие образца записи), `05_SQL_SERVICE_LOGINS.sql`
(учётные записи API), `06_BOT_CONSENT.md` (согласия в боте).

---

## 1. Цель

Пациент сети (Каширка, Куркино, Куркино 2) в браузере телефона и в мессенджере MAX:
- видит предстоящие записи и историю посещений (даты приёмов);
- сам записывается в расписание, переносит и отменяет приём;
- получает напоминания и подтверждает визит;
- видит подключённые программы: страхование (ДМС), программы прикрепления, акции,
  депозит, задолженность;
- смотрит результаты анализов.

Принципы:
- МИС Медиалог — единственный источник правды о записях, программах и деньгах.
- Чтение из Медиалога — постоянно. **Запись в Медиалог разрешена только через
  утверждённые этим ТЗ пути**, только с учётной записи с узкими правами и на пилоте —
  только для пациентов и расписаний из белого списка владельца (D1).
- Всё, что ЛК создаёт сам (входы, подтверждения, журнал действий), хранится в собственной
  базе сервиса (`gateway.db`).

## 2. Границы

**Входит:** API (`medkvadrat-patient-api`), бот (`medkvadrat-max-bot`), веб-интерфейс
пациента (новый репозиторий `medkvadrat-patient-web`), деплой (`medkvadrat-deploy`),
staff-дашборд расписания (уже есть).

**Не входит:** изменение настроек, справочников и схемы Медиалога; оплата онлайн;
клинические данные ЭМК — диагнозы, протоколы, заключения (D7); SMS-шлюз (D3);
заявки в колл-центр как замена записи (D5).

## 4. Этапы

### Этап 0. Фундамент и ограждения

1. **Белые списки write** вместо выключения (D1):
   - `MEDIALOG_WRITE_ENABLED` (по умолчанию `false`) — общий выключатель;
   - `MEDIALOG_WRITE_ALLOW_PATIENTS` — `PATIENTS_ID`, для которых разрешена запись
     (пилот: `1,1587578`); пусто → никому;
   - `MEDIALOG_WRITE_ALLOW_PL_SUBJ` — линии расписания, в которые разрешено писать
     (пилот: тестовая линия; см. 04); пусто → никуда;
   - вне списков — `403 WRITE_NOT_ALLOWED` до обращения к базе.
2. **Журнал write** в `gateway.db`: время, `request_id`, `patient_id`, `planning_id`,
   действие, результат, код ошибки. Без ФИО.
3. `MotconsuPoller` выключен по умолчанию (`MOTCONSU_POLL_ENABLED=false`).
4. `app name=medkvadrat-patient-api` в строке подключения; две строки подключения —
   чтение и запись (§7.2).
5. CORS по списку `CORS_ALLOWED_ORIGINS`.
6. `/api/health` различает «API жив» и «Медиалог доступен».
7. Документы проекта и шаблон PR в репозиториях.
8. **Закрыть ошибочный путь «свободных слотов»** (S1, 15.10.2026): `GET /api/catalog/slots`,
   `GET /api/schedule/slots` и `POST /api/schedule/book` считают свободными строки
   `PLANNING` без `PATIENTS_ID`, а это записи новых пациентов; запись по ним перезаписывает
   чужую запись. До этапа 2 эти пути отвечают `503 FEATURE_DISABLED` без обращения к базе.
9. **Логин только на чтение** `svc_patient_api_ro` (§7.2) — сразу, не дожидаясь этапа 2.

### Этап 2. Онлайн-запись в расписание (D5)

Запись создаётся сразу в `PLANNING`. Колл-центр не участвует.

**Новое (15.10.2026, S17).** В базе есть штатная процедура онлайн-записи Медиалога
`pl_AddVisit` / `pl_AddVisitContext` — через неё пишут Мобимед, веб-запись и инфоматы. Она
сама проверяет WEB-доступ линии и вида приёма, горизонт и лимиты записи, конфликты пациента
и врача, исключения сетки, блокировки, рабочее время и вставляет строку атомарно (занятое
время не займёт). Использовать её вместо повторения действий клиента — надёжнее и ближе к
задумке разработчика МИС. Решение — Q17, после S18 (текст `pl_AddVisitContext`, процедура
отмены, «веб-пользователь», подписки HL7). Для этого варианта логину на запись нужен только
`EXECUTE` на 2–3 процедуры, а запись в таблицы — запрещена (процедуры владельца `dbo` пишут
по цепочке владения).

Этап делится на исследование (только чтение + один контролируемый опыт
владельца) и разработку.

## 6. Интерфейс пациента

- Репозиторий `medkvadrat-patient-web`, статический фронт за обратным прокси.
- Mobile-first. Экраны: вход → выбор профиля → «Мои записи» (ближайшая сверху: «Подтвердить»,

- Позже — мини-приложение MAX поверх того же фронта.

## 7. Нефункциональные требования

### 7.1 Безопасность и ПДн

- Данные о здоровье — специальная категория ПДн (152-ФЗ). Уровень защищённости ИСПДн
  и меры определяет ИБ до публикации наружу (D6).
- Согласия (D4): без отметки e-mail нет входа в ЛК; без отметки «Мессенджеры» нет кода и
  напоминаний в MAX. Отсутствие анкеты (`NULL`) = нет согласия.
- Код входа: 6 цифр, 5 минут, лимиты по телефону и IP, блокировка после серии ошибок;
  ответ не раскрывает, есть ли пациент с таким телефоном.
- Пациент видит и меняет только своё: `patient_id` только из JWT; чужой `planning_id` → `404`.
- Логи — только идентификаторы (`MEDIALOG_RULES.md`).

### 7.2 Учётные записи базы (ответ на D2)

Сейчас API ходит в Медиалог под **личной** учётной записью сотрудника, и всё, что делает
API, в журналах выглядит как действия этого человека. Если пароль из `.env` утечёт или в
коде будет ошибка, пострадать может любая таблица.

Проверка 15.10.2026 показала больше: роли `public` в `Medialog` выданы
`INSERT/UPDATE/DELETE/ALTER` почти на все таблицы и `EXECUTE` на все процедуры. Права
`public` получает любой пользователь базы, поэтому роль `db_datareader` сама по себе не
делает логин «только чтение». Нужны явные запреты (`DENY`) на уровне базы.

Решение — две **служебные** учётные записи SQL Server, только для API:

| Логин | Права | Кто использует |
|---|---|---|
| `svc_patient_api_ro` | `db_datareader` + `DENY INSERT/UPDATE/DELETE/ALTER/EXECUTE/REFERENCES` и создания объектов на уровне базы; `DENY CONTROL` на 6 объектов с `CONTROL` у `public`; `DENY SELECT` на `DS_RESMSGTYPES` (пароли SMTP) | все read-пути; создаётся сейчас |
| `svc_patient_api_rw` | только то, что нужно образцу R4; **не создаётся до R4**: через `public` получил бы запись во всё, а запрет на уровне базы перекрыл бы и нужное. Варианты — в файле 05, блок 5 | только write-пути этапа 2, за белыми списками |

Следствие для кода: служебному логину запрещено выполнять процедуры и функции Медиалога.
Read-пути их не вызывают; проверку email (`fnEmailCheck`) API делает своим кодом по тем же
правилам; для денег этапа 3 — отдельное решение (§4, этап 3).

Плюсы: ошибка в read-коде физически не может ничего изменить; права write ограничены
столом расписания; в `sys.dm_exec_sessions` и трассировках действия API видны отдельно;
пароль сотрудника не лежит в конфиге. Создаёт логины владелец скриптом
`05_SQL_SERVICE_LOGINS.sql` (в базе появятся только пользователи и права, таблицы и данные
Медиалога не меняются).

### 7.3 Нагрузка на базу

- Каждый запрос ограничен пациентом или датой, тайм-аут 10 с; без полных сканов
  `PATIENTS` (1,6 млн) и `PLANNING` в пользовательском пути.
- Поиск по телефону — без `LIKE '%…%'` по всей таблице (кэш нормализованных телефонов
  или иной способ, отдельный PR).
- Справочники и сетка расписания кэшируются (10–60 мин и 1–2 мин соответственно).
- Читаемой реплики нет (Always On не настроен, S6) — все чтения идут в основную базу; отсюда требования к окнам и кэшу.

### 7.4 Надёжность и наблюдаемость

- Медиалог недоступен → «данные временно недоступны», write не выполняется.
- Бэкап `gateway.db` ежедневно.
- Метрики: входы, ошибки кода, записи/переносы/отмены (успех, конфликт, ошибка),
  время ответа Медиалога.

## 10. Приёмка

**Этап 0:** запись в Медиалог из API для пациента и линии вне белых списков → `403`
без обращения к базе; пути «слотов» → `503`; блок 3 файла 05 показывает нули для
`svc_patient_api_ro`, и API на нём работает на чтение; журнал write заполняется; API виден в `sys.dm_exec_sessions` как
`medkvadrat-patient-api`; тесты зелёные.

**Этап 1** (стенд, профили `1` и `1587578`): реальные записи и визиты совпадают с S3;
пациент без отметки e-mail не может войти; чужой `planning_id` → `404`; в логах нет ПДн;
`/api/me/appointments` < 1 с.

**Этап 2:** владелец на тестовой линии делает запись, перенос и отмену через ЛК; в
клиенте Медиалога результат выглядит так же, как после тех же действий в самом клиенте
(сравнение с образцом R4 поле за полем); попытка записи на занятое время → `409`;
повторное нажатие не создаёт дубль; integration-тесты зелёные. Снятие белых списков —
отдельное решение владельца.

**Этап 3:** программы, депозит и долг на профиле владельца совпадают с окном «Медицинские
программы» и лицевым счётом в клиенте Медиалога.
